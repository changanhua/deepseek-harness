# Agent Note: FC 27 SBC assistant

Status: proposed

English | [中文](2026-09-25-fc27-sbc-assistant.zh.md)

## Problem

A personal browser assistant can operate an FC Web App page, but generic page actions cannot decide which owned cards to consume, which missing cards to buy, or whether a submitted SBC actually completed. Price errors and unknown purchases can spend Coins or consume irreplaceable cards. The user wants one reviewable SBC plan followed by automated acquisition and completion without repeated per-card permission prompts.

## Proposal

Add an FC 27 puzzle-SBC capability through the existing browser assistant entry. Read one challenge set, club and SBC Storage inventory, confirm Web App market access, and collect versioned market quotes; solve all challenges against one shared card pool. Show owned cards, protected cards, missing card versions, per-card maximum prices, total budget, and the exact submission scope. One direct, time-bounded user approval binds that plan. A deterministic controller then purchases the missing cards under a persisted reserved-and-spent budget ledger, reconciles inventory after acquisition and each submission, fills each challenge, checks EA's displayed requirements, and submits only the approved challenges. It retains request identities and readback evidence for every irreversible action. Browser site consent persists; a changed or expired plan requires a new plan approval.

The [detailed design](../../../../docs/specs/2026-09-25-fc27-sbc-assistant.md) owns the workflow, minimum domain records, failure states, risk controls, delivery slices, and evidence requirements. FC 27 simplified Item Score SBCs require a separate solver and executor because partial submissions consume cards; the first vertical covers traditional puzzle SBCs only.

## Current implementation slice

This slice now also gives each approval preview a stable review digest and normalized session/installation/tab/club/page/inventory identity, and carries that digest through readiness, the redacted report, the JSON sample, and the sidebar preview so later execution can detect when reviewed inputs no longer match execution inputs.

It also adds `apps/chrome-extension/src/fc-sbc-execution-gate.js`, a pure pre-execution gate for later write actions. The gate compares the reviewed digest, current identity, approval window, same-tab write lease, purchase price limit, and submit/fill scope, then returns ready or blocked without buying, filling, submitting, or writing the browser.

`apps/chrome-extension/src/fc-sbc-write-lease.js` defines the matching pure write-lease record: it can issue, validate, and release a time-limited lease bound to the approval digest and page identity, and released leases now block the execution gate. It still does not acquire a live browser lock or dispatch any write action.

The first source slice adds `apps/chrome-extension/src/fc-sbc-core.js` and a typed declaration. It can rank whole-group candidate squads without reusing owned card instances, reject locked cards and stale or unobserved quotes, create time-bounded plan approvals, reserve purchase budget before a request, settle confirmed or unknown purchases, and require EA page readback before a submit request counts as complete. It now rejects submit approval scopes that are outside the selected plan. `apps/chrome-extension/src/fc-sbc-page-probe.js` adds a self-contained read-only DOM probe that reports recognized FC pages, puzzle versus Item Score task type, visible challenges, market-access text evidence, and visible-only inventory coverage. `apps/chrome-extension/src/fc-sbc-inventory-snapshot.js` adds a pure complete-inventory snapshot contract that normalizes already-read club, SBC Storage, and visible card rows into solver-safe instances, counts Storage/locked/tradeable cards, rejects missing identities or duplicate instances, and records unproven coverage without scraping EA itself. `apps/chrome-extension/src/fc-sbc-transaction-readback.js` adds a pure transaction-readback contract that classifies already-observed purchase additions, actual price, balance movement, challenge completion, and card-pool delta as confirmed, completed, unknown, or blocked without sending buy or submit actions. `apps/chrome-extension/src/fc-sbc-field-audit.js` turns probe, inventory snapshot, and transaction readback results into page/task/market/inventory/readback field coverage, explicitly flagging missing real-page samples such as complete club inventory acquisition, purchase readback, and submission readback. `apps/chrome-extension/src/fc-sbc-quote-preflight.js` adds a pure quote and risk preflight for same-platform fresh positive quotes and a market-search ceiling; missing, stale, invalid, mismatched, or over-limit quote state blocks approval before any purchase. `apps/chrome-extension/src/fc-sbc-execution-dry-run.js` adds a pure execution preview that derives a purchase queue and submission queue from a candidate plan or approval snapshot, computes reserved spend and per-card search ceilings, and reports budget or search-limit blockers while keeping browser writes, purchases, squad fill, and submits false. `apps/chrome-extension/src/fc-sbc-risk-preflight.js` adds a pure exposure preflight that quantifies planned purchases, market searches, submits, market visibility, and unknown transaction readback while explicitly stating that it cannot prove a ban-free method. `apps/chrome-extension/src/fc-sbc-approval-preview.js` adds a pure approval preview that summarizes selected plan scope, budget, purchase count, submit count, default approval windows, execution preview, and risk state without producing a real approval or browser action. `apps/chrome-extension/src/fc-sbc-readiness.js` combines the probe, inventory snapshot, transaction readback, field audit, quote preflight, execution dry-run, risk preflight, approval preview, and solver input into approval blockers, deferred follow-up gaps, and a next safe action, so incomplete page, inventory, transaction, price, execution, risk, approval scope, or solver coverage becomes an explicit draft-only state instead of an attempted run. Execution dry-run or risk preflight blocked states now close final approval. `apps/chrome-extension/src/fc-sbc-comb-report.js` formats a redacted first-pass handoff report that keeps page status, counts, blockers, deferred gaps, field gaps, quote coverage, approval-preview summary, and visible requirement/reward lines while dropping URL query strings, private instance IDs, card text samples, and raw DOM snippets. `apps/chrome-extension/src/fc-sbc-redacted-sample.js` formats a machine-readable JSON sample with the same privacy boundary plus inventory statistics, quote preflight, aggregate inventory snapshot summary when available, transaction readback status summary when available, execution dry-run, risk preflight, and approval preview when available, and privacy flags. The extension sidebar now has an `SBC` tab that runs the read-only probe against the fixed target page, displays readiness blockers, deferred gaps, field coverage counts, field gap labels, any no-side-effect execution dry-run, risk exposure counts plus the ban-risk disclaimer, and approval-preview budget/scope counts, previews the redacted report, and sends either the report or the JSON sample to the current conversation only after the user clicks the corresponding handoff button. `apps/chrome-extension/src/assistant-runtime.js` exposes the planning and probe/readiness pieces only through the read-only `dsh-assistant-fc-sbc-plan`, `dsh-assistant-fc-sbc-probe`, and `dsh-assistant-fc-sbc-readiness` messages. It does not yet scrape complete FC inventory from EA, prove real market access, purchase cards, fill squads, submit SBCs, persist a domain run, or enforce the same-tab write lease.

## Ownership boundary

Reuse the existing Browser definition, authenticated Chrome provider, exact page identity, grant epoch, request journal, and status lookup. Keep FC challenge parsing and page-specific interaction in an extension adapter, market quotes in a replaceable provider, and optimization in a local solver. A Session-backed domain run owns the immutable approval, budget ledger, action ledger, and result; its model tools can read and propose plans, while only the plan-bound domain executor can purchase or submit. During a run, a page-scoped Browser policy denies other DSH Sessions' writes to that tab. Model prose cannot authorize additional spending or turn a local click receipt into business completion. The existing generic BrowserTask continuation and action budget do not own an entire multi-challenge purchase run.

This proposal supplements the [personal browser assistant V2 proposal](2026-09-20-personal-browser-assistant-v2.md) and the active Browser operation decisions. It changes no generic target, permission, or cleanup rule; neither proposal supersedes the other.

## Alternatives considered

**Copy the current FodderGG client and solver.** Its distributed userscript loads changing remote code and its hosted solver is not a confirmed licensed source for DSH; use its FC 27 workflow as a product reference, not as a vendored dependency.

**Ask the model to click through the whole set with generic Browser tools.** This leaves price limits, card identity, approval scope, and unknown transaction recovery in unstructured prompts while the generic task loop has bounded actions. A domain plan and deterministic executor keep those obligations explicit.

**Require a separate approval for every card.** This adds friction after the user has approved the exact card list and limits. One plan approval covers listed purchases and submissions; anything outside it pauses for a revised plan.

## Acceptance criteria

A real FC 27 Web App puzzle-SBC set runs from the installed DSH extension after one approved plan. The user sees actual purchases, consumed card instances, balance changes, completed challenges, rewards, and unresolved actions. A real missing-card purchase, squad fill, and approved submission are independently verified from EA page state. Missing market access blocks execution before approval; unknown purchases keep their budget reservation and never cause blind retries; stale prices, changed targets, locked cards, expired approval, cross-Session writes, and budget overruns stop execution. Source, generated, composed, runtime, and behavior evidence all agree before the Epic is called complete.

## Risks

EA forbids in-game automation and explicitly names auto-buyers; fewer actions and spending bounds do not establish a ban-free method. Price sources can be stale, browser permissions or page models can drift, and a submission cannot be undone. The first delivery must verify current FC 27 fields and transaction readback on a real account before claiming live support; no existing code or third-party plugin is evidence that this vertical already works.
