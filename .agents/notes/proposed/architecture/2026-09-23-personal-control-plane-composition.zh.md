# Agent Note：个人控制平面作为组合层

状态：proposed

[English](2026-09-23-personal-control-plane-composition.md) | 中文

基线：`changanhua/deepseek-harness` `master@6ddb5ca503da7b8a0da286a716565963efcb2f50`

## 背景

DSH 服务于一个可以不断更换模型提供商、但需要持续保留项目、账号、工具、进行中的工作、证据和决策的单一所有者。随着模型进步，规划、编码、浏览、总结、路由、审查等认知策略都可能被替换。因此，DSH 的耐久价值不应是包在模型外面的第二层智能，而应是跨模型变化保存真实状态、意图、权限和证据的所有者控制层。

一个朴素的个人控制平面实现，可能会新建通用的 `WorkItem`、`StateFact`、`Evidence` 和 `Decision` 表。但当前基线已经存在语义更窄、约束更强的权威域：

- [Personal Delivery](../../../../docs/subsystems/delivery.zh.md) 负责需求采纳、不可变修订、边界明确的工作包、产物、验证报告和人工验收决策。
- [Project Memory](../../../../docs/subsystems/project-memory.zh.md) 负责有来源支撑的项目主张、提案、审查、接纳、冲突、替代、过期、撤回和保留。
- Workspace、Content、Queue、Session、BrowserTask、Credentials、Interaction 和 Context 已分别拥有范围、来源、执行、轨迹、行动、权限、审批与上下文装配语义。

在它们上方再建立一个持久权威，会复制状态、产生对账负担，并让控制平面成为下一个单体系统。当前真正缺少的是组合能力：一个与模型无关的个人世界视图、一个按权威域路由的命令入口，以及一条把已验收工作明确提议为耐久项目知识的路径。

## 决策

个人控制平面是一个架构组合层，而不是新的持久权威域。

版本 1 禁止引入通用控制平面数据库、通用事实库或第二套工作生命周期。它从现有权威派生读取模型，把写操作路由给这些权威，并保留回到规范记录的来源链。

组合层只有三项职责：

1. 从权威记录生成与模型无关的 `PersonalControlSnapshot`。
2. 将 `ControlCommand` 路由给拥有目标状态转换的领域。
3. 将被选择且已验收的交付结果转换为 `MemoryProposal` 候选，但不得自动接纳。

组合层不能因为模型或 UI 读取了它就成为权威。模型回答、Session 轨迹、生成式摘要或控制快照本身都不是真实状态。

首个实现不需要创建名为 `control-plane` 的包。第一版投影应放在现有应用层或 bundle 的组合边缘。只有至少两个独立消费者需要同一稳定契约时，才可以抽取专用包。

## 权威映射

| 关注点 | 规范权威 | 控制平面用途 | 禁止复制 |
| --- | --- | --- | --- |
| 个人或项目范围 | Workspace | 选择活动范围并解析范围内服务 | 第二套 workspace 注册表 |
| 来源文档、草稿、版本和存储产物 | Content 与专属证据存储 | 引用不可变来源或产物修订 | 把来源正文复制进控制记录 |
| 耐久项目命题 | Project Memory | 读取已接纳主张；提交待审提案 | 直接把模型摘要写成已接纳事实 |
| 需求、边界工作、验证和验收 | Personal Delivery | 展示活动 case 并路由交付状态转换 | 第二套 WorkItem 或验收状态机 |
| 执行调度与尝试 | Queue | 引用当前执行及结果 | 把 Queue 状态当作产品验收 |
| 原始执行轨迹 | Session | 提供追踪和恢复上下文 | 把轨迹或最终回答当作真实状态 |
| 浏览器目标、资源所有权和任务生命周期 | BrowserTask | 展示可用权限引用 | 把浏览器所有权复制到记忆 |
| 临时权限和人工审批 | Credentials 与 Interaction | 展示活动租约和待决事项 | 持久化秘密或绕过审批 |
| 模型专用上下文装配 | Context | 从快照编译提供商可用视图 | 让编译后的上下文成为规范记录 |
| 单轮目标评估 | Goal | 提供可选评估信号 | 把评估输出自动变成决策 |

此前概念中的对象应映射到现有记录，而不是新表：

| 概念对象 | 现有表示 |
| --- | --- |
| Work Item | `DeliveryCase` + `RequirementContract` 或 `ContractRevision` + `WorkPacket` |
| Evidence | `DeliveryArtifact` + `VerificationReport` + 类型化 `EvidenceRef` |
| Decision | case 结果使用 Delivery `DecisionRecord`；耐久知识使用 Project Memory 审查与已接纳主张状态 |
| State Fact | 由所属领域保存的当前记录；只有真正耐久的命题才表示为有来源且已接纳的 `MemoryClaim` |

短暂运行状态继续由 Queue、Session、BrowserTask、Credentials 或 Interaction 持有。它可以按引用出现在快照中，但不得仅为了统一视图就复制进 Project Memory。

## PersonalControlSnapshot

`PersonalControlSnapshot` 是针对某个 workspace 与用途生成的不可变派生读取模型。它可以丢弃并重新生成，并携带足够的来源信息，使消费者能读取或验证每一项重要主张。

版本 1 的快照包含四个视图：

- **Truth：** 已接纳的 Project Memory 主张、固定的 Content 修订，以及各权威域的当前状态引用。
- **Intent：** 活动 Delivery case、冻结的需求修订、边界明确的工作包、约束与验收标准。
- **Authority：** 可用 BrowserTask 引用、凭据租约元数据、待处理 Interaction 决策和被允许的命令集合；绝不包含秘密。
- **Evidence：** 交付产物、验证报告、决策记录，以及必要时指向原始 Session 或 Queue 轨迹的链接。

每个快照都包含 `schemaVersion`、`generatedAt`、workspace 身份、权威记录标识、可用的权威修订或新鲜度标记，以及来源链。消费者必须显式处理缺失、过期、撤回、被替代或不可访问的来源记录，而不能用模型推断静默补齐。

快照可以为了传输而缓存，但缓存不是权威。任何改变状态的命令，都必须重新验证相关权威修订或前置条件。

## 控制命令与写入路由

控制命令表达用户或模型的意图，但不拥有由此产生的状态。组合层负责校验范围，并把命令路由到规范服务。

代表性命令包括：

- 通过 Delivery 打开或修订交付 case；
- 通过 Delivery 冻结需求修订或签发 WorkPacket；
- 通过 Delivery 及其证据提供者记录产物或请求验证；
- 通过 Delivery 的人工决策路径接纳、拒绝、修订或关闭；
- 通过 Project Memory 提交 `MemoryProposal`；
- 通过 Interaction 请求审批；
- 通过 Credentials 获取或使用临时权限；
- 通过与 Session 绑定的 BrowserTask 权威执行浏览器动作。

版本 1 禁止暴露通用的 `writeFact`、`setState` 或 `markDone` 命令。这类命令会抹掉所有权边界，并允许模型把自己的叙述晋升为真实状态。

每个被路由的命令都记录发起者、适用时的模型与 Session、workspace、目标权威、目标记录、预期修订或前置条件、结果引用和审计时间。领域专属审计记录仍然是规范记录。

## 从已验收工作晋升为耐久记忆

学习边界是刻意不对称的：

```text
Session 或 Queue 轨迹
        -> Delivery 产物与验证
        -> 人工 Delivery 决策
        -> 可选 MemoryProposal
        -> Project Memory 审查
        -> 已接纳 MemoryClaim
```

被拒绝、放弃或仅仅执行完成的 Session 不能自动更新耐久 Project Memory。即使一个 Delivery case 已被接纳，也不意味着每一条观察都应该成为记忆。

一个晋升候选必须说明：

- 拟议的耐久命题；
- 为什么该命题预计会影响未来工作；
- 支撑它的来源修订、产物、验证报告和决策记录；
- 预期范围与新鲜度或过期预期；
- 它是否替代现有已接纳主张，或与其冲突。

首个实现只在明确的人工动作之后创建草稿或待审 `MemoryProposal`。以后可以评估自动生成提案，但自动接纳不属于版本 1。

当前 Queue attempt、即将过期的凭据租约或短暂 BrowserTask 状态等运行细节不是晋升候选，除非它们用于支撑另一个耐久命题。

## 第一个垂直切片

第一个切片使用 DSH 完成一项真实的 DSH 仓库任务，不建立仅供演示的流程。

1. 选择 DSH workspace 和一个活动 Delivery case。
2. 冻结或选择需求修订与边界明确的 WorkPacket。
3. 从已接纳 Project Memory 主张、Delivery 契约、当前权限引用和既有证据生成 `PersonalControlSnapshot`。
4. 把同一个快照契约交给一个可替换的执行模型。
5. 通过现有 Session、Queue、BrowserTask、仓库和凭据边界执行。
6. 将输出保存为 Delivery 产物，并运行独立验证。
7. 强制产生明确的 Delivery 决策：接纳、拒绝、修订或阻塞。
8. 接纳后，由用户明确地从选定结果创建零个或多个 Project Memory 提案。
9. 生成新快照，并证明另一个模型无需迁移权威或重放完整对话即可继续工作。

只有当被拒绝工作无法改变耐久真实状态、被接纳工作有可检查证据支持，并且更换模型不需要在权威记录之外重新解释项目时，这个切片才算成功。

## 实施顺序

### PR0：架构决策

本文记录所有权、负面保证、首个切片与止损条件，刻意不改变运行时行为。

### PR1：只读控制投影

在现有组合边缘增加版本化 `PersonalControlSnapshot` 查询。复用现有 Delivery、Project Memory、Workspace、Content、Interaction、Credentials、Session、Queue 与 BrowserTask 读取契约。禁止增加新的持久表，也不创建 `packages/control-plane`。

第一个消费者应是现有 Personal Delivery 工作台或一个狭窄的服务器端点。只有契约拥有两个独立消费者之后，才考虑抽包。

### PR2：路由命令与证据连续性

只暴露垂直切片所需的有限命令。保留预期修订、发起者身份、来源引用与审计连续性。验收仍然是 Delivery 中的人工决策。

### PR3：显式晋升桥

从已接纳 Delivery 决策预填一个带证据引用的 Project Memory 提案。用户可以编辑、提交或丢弃；任何主张都不得被自动接纳。

### PR4：模型替换评估

使用至少两个模型提供商运行同一快照和命令契约。比较完成情况、证据、token 与延迟成本、所需重复解释，以及是否有提供商专用逻辑泄漏进权威域。

## 验收标准

只有全部满足以下条件，首个实现才可被接纳：

- 没有引入新的规范数据库或重复工作生命周期；
- 快照中的每一项重要内容都能解析到权威记录；
- 过期或被替代的输入清晰可见，命令会执行相关前置条件；
- 模型不能自行把工作标记为已验收，也不能写入已接纳 `MemoryClaim`；
- 被拒绝工作不会在已接纳项目记忆中留下残留；
- 被接纳工作有可检查产物、验证与人工决策；
- 第二个模型无需重放对话即可从权威状态继续 case；
- 删除并重建快照不会丢失任何规范状态；
- 提供商专用 prompt 与策略仍然位于权威记录之外。

## 止损条件

完成五项真实 DSH 任务后，如以下任一情况持续存在，应停止或删除组合层：

- 操作者必须在快照与另一个控制平面数据库之间对账；
- 快照变成需要人工维护的总结；
- 多数字段只是在重命名既有 DTO，既没有减少重复解释，也没有改善验证；
- 晋升产生的过期、重复或冲突主张多于有用的耐久知识；
- UI 成为唯一能理解状态转换的位置；
- 更强模型因为必须遵循固定编排仪式，而无法直接使用权威服务。

完整组合层失败，并不意味着应删除现有权威域；它只说明该投影或命令入口没有赚回维护成本。

## 后果与风险

该决策减少了绿地实现，但提高了对精确跨域契约的要求。现有权威可能采用不同的修订、新鲜度与身份约定；快照必须暴露这些差异，而不是把它们压平成虚假的统一。

主要架构风险是形成新的上帝层。通过三项负面保证缓解：

1. 组合层不拥有任何规范业务状态；
2. 权威服务在没有组合层时仍可独立调用和测试；
3. 命令不能绕过权威校验、修订检查、审计或人工审批。

主要产品风险是做出一个看起来很厉害、却没有改善工作的仪表盘。因此第一个切片会在扩大 UI 投入之前，测量重复解释、证据完整度、拒绝隔离和模型替换。

主要学习风险是记忆污染。Project Memory 现有的提案与审查生命周期仍是强制边界。大多数 Session 和许多已验收交付都不应产生耐久主张。

## 非目标

版本 1 不建设：

- 通用个人本体或知识图谱；
- 自动分析每一个 Session；
- 固定的 Planner/Executor/Critic/Supervisor 流水线；
- 第二套任务队列、workspace 存储、证据库或审批系统；
- 模型训练、强化学习或微调；
- 通用跨域变更语言；
- 精装修的个人操作系统仪表盘；
- 自动接纳生成式记忆。

## 验证计划

文档验证遵循仓库的双语配对与 docs-only 检查。运行时 PR 必须增加权威边界测试、快照来源测试、过期修订测试、拒绝隔离测试和端到端模型替换场景。

首个运行时 PR 必须明确它扩展的现有组合边缘，列出读取的每一个权威 API，并证明当前尚无抽取包的必要。任何新增持久控制平面存储的提案，都需要新的架构决策，并给出无法由现有权威表达的具体案例。
