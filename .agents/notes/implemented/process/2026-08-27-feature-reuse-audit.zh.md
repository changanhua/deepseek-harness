# Agent Note: DSH 设计前执行基于证据的功能复用审计

Status: implemented

[English](2026-08-27-feature-reuse-audit.md) | 中文

## 问题

功能设计可能从用户提出的机制直接开始，而没有先检查 DSH 已有的 Service Definition、Service Provider、Consumer、WorkKind、Skill、运行时组合和生效中的决策。包名或源码搜索因而被误当成能力覆盖证据；社区仓库则可能被忽略，或者在尚未检查生命周期、权限、脚本、许可证和 Provider 假设时就被当成可直接采用的依赖。结果是重复实现运行时行为，或者为了连接已经有稳定所有者的能力而引入过大的抽象。

## 决策

仓库提供 [`dsh-reuse`](../../../skills/dsh-reuse/SKILL.md) 工作流，在为存在不确定性的功能提案编写实施计划之前使用。它从用户结果出发，按语义搜索当前 DSH 的定义、实现、组合、Consumer、测试和生效中的决策依据，再检查相关 Profile，以及对应 scope 可见的 Skill、Tool、MCP 条目和 WorkKind。只有明确本地语义缺口之后才开始搜索社区，而且在用户授权安装或实施之前始终只读。

工作流给出 `direct reuse`、`adapt`、`bridge`、`vendor/fork` 或 `build` 之一，并附带证据类别、依赖方向、最小必要新增代码、非目标、验证方式、置信度和时效说明。它记录当前分支和 worktree 状态，并区分已经提交的源码、当前 checkout 中尚未提交的 WIP、已安装但未评估的候选、仍处于提案阶段，以及已经通过运行时验证的能力。没有搜索命中不等于能力不存在，未提交源码也只能证明存在重叠工作，不能证明能力已经交付。

复用必须保留 DSH 的能力所有权。Consumer 依赖 Service Definition，而不是具体 Service Provider；跨领域集成使用可逆的 Bridge 插件；Bundle 选择 Provider 和部署配置。审计生成或撰写的能力清单只是一种开发期投影，不能成为第二套运行时注册表，也不能成为产品插件的依赖。

社区能力引入记录固定版本、许可证、脚本、网络与凭据行为、文件系统写入、输出校验、模型假设、评估证据和更新方式。搜索结果、star 数和安装量只能帮助发现候选，不能赋予采用权限。可以固定并约束有价值的指令包，而不引入与目标无关的 Provider 执行脚本。

已经明确范围的机械改动，或者所有者已知的缺陷修复，不选用这项工作流。[`dsh-find-simplifications`](../../../skills/dsh-find-simplifications/SKILL.md) 继续负责对已经交付的重复实现、无效行为和过度设计进行广泛审计；功能复用审计则在不确定的新接口落地前阻止重复建设。

## 曾考虑的替代方案

- **只在根级指令中加入“开发前先搜索”规则**：不予采纳。简短的常驻规则无法承载搜索来源、社区引入检查、生命周期比较、依赖判断、报告格式和校准示例；把这些内容全部加载到每个会话又会浪费上下文。
- **创建所有插件都要查询的中央运行时能力注册表**：不予采纳。Cordis Service 与 `inject` 已经负责运行时发现；另一套权威会重复注册逻辑，并让原本独立的产品插件依赖开发期情报。
- **先搜索社区注册表，再阅读 DSH**：不予采纳。名称和流行度无法说明本地所有权、组合、持久性或权限；外部候选也可能只是用另一个术语重复 DSH 已经交付的行为。
- **扩展 `dsh-find-simplifications` 以覆盖功能提案**：不予采纳。它面向实现后的广泛调查、删除证据和 Agent Note 合并，明显重于有时间上限的设计前决策，而且两者的完成条件不同。

## 后果

存在不确定性的新功能会在实施前付出有界的证据成本，报告会要求新包或新状态机准确说明现有能力缺失的语义。Direct reuse 和 Bridge 不再是在编码途中偶然发现的方案，而成为显式候选。社区能力的采用增加了来源记录和评审成本，但避免了未固定版本的执行和隐藏副作用。机械改动继续使用仓库快速路径，产品插件也不会依赖这项审计工作流或其可丢弃的搜索投影。
