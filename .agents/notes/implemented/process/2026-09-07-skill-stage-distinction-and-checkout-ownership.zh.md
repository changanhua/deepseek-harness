# Agent Note: Skill 阶段区分与 checkout 归属

Status: implemented

[English](2026-09-07-skill-stage-distinction-and-checkout-ownership.md) | 中文

## Problem

文档与 Charter 类 Skill 此前把「对话中的产品提问」「本地设计草稿」「实现准备」当成同一种工作：任何 Markdown 都可能触发 package README 模板、双语对齐、完整 `test:docs`/`doc-sync`/lint 车道，以及带仓库发现的 Charter receipt。探索与本地原型付出了维护文档的成本，而在这些义务被推断出来之前，也没有规则说明目标属于哪个 checkout 或 package。

## Decision

文档与特性规划类 Skill 在加载模板或运行检查之前，先区分三个被请求的阶段：探索或解释（在对话中回答）、起草设计（产出所请求的场景/对象/操作设计，把已接受方向与建议细节分开）、准备实现（只冻结已批准范围需要的决策，走完整模板与证据规则）。方向获批不等于每个细节或实现获批。

本地设计草稿——例如 `ui-prototype/` 交互原型——不会因为它是 Markdown 就成为实现产品文档。它保留用户的语言、proposed/current 区分、出处和开放问题；提交可以保留其版本历史，但不要求 README 骨架、双语对侧或仓库构建车道。维护文件先解析 [checkout 与 package 归属](../../../skills/dsh-reuse/references/checkout-ownership.md)：个人 checkout 拥有自己的对齐排除项与命令，放置跟随产物的真实生命周期与受众，而不是为了规避必须的检查。

检查从目标的脚本与实际受影响语料中选择。聚焦检查不证明更宽的车道通过；综合车道也不是本地草稿或聚焦文字修改的默认前置。事实核对区分「声明的源码契约」与「观察到的行为」：源码能确立一个被声明的默认值，只有被识别的运行时才能证明它处于激活状态；且验证要求绝不授权安装、使用凭证、花费、发布或重启服务——未验证的操作被点名并给出验证 owner，而不是被断言。

[简化 Skill](../../../skills/dsh-find-simplifications/SKILL.md) 将这一区分应用于审查、清理和发布。审查报告证据，不创建笔记或 TODO；已授权的修改依据当前工作区与实际分支基线，并遵循权威 Agent Note 格式和保留规则。分支归属不授予发布或关闭 PR 的权限。消费方发现依据 manifest（元数据清单）、入口、动态注册和公共约定，而不是固定目录列表；必要的生命周期保护仍属于候选评估的一部分。

## Alternatives considered

**对所有 Markdown 保持单一严格流程。** 拒绝：它让探索与本地草稿承担维护文档的全部成本，要么压制设计讨论，要么让仓库充满仪式性产物。

**让每个 Skill 自行定义草稿例外。** 拒绝：阶段区分是横切标准；同一放宽的多份拷贝会漂移并随时间再次分叉。

**把草稿完全挡在仓库之外。** 拒绝：提交原型保留了可评审的历史与低成本回退，而其非权威状态通过草稿规则本身保持可见。

## Consequences

探索在对话中作答、设计草稿保持轻量；维护文档保留完整门禁，聚焦检查不再默默声称综合验证。`dsh-doc` 的触发范围收窄到实际 owner 规则下的维护文档，`dsh-feature-charter` 支持探索而不强求 receipt、仓库审计或书面文件。放置问题在 package 选择之前先咨询 checkout 归属，上游示例或另一个 checkout 的 skill 不能决定本实现拥有什么。未验证的操作如实上报并点名验证 owner，权限或环境的缺失不再产出虚构证据。
