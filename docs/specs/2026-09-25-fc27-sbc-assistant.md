# FC 27 SBC 助手整体设计

续接入口：[FC Web App 应用模型与 Agent 自动化交接](2026-09-26-fc-web-app-model-handoff.md)。该交接负责当前的架构方向和落地顺序；本文保留 SBC 领域问题与候选实现设计，不作为先建设完整 SBC 专用平台的要求。

状态：设计提案，已开始部分实现；`apps/chrome-extension/src/fc-sbc-core.js` 落地了整组候选方案选择、批准期限、预算预留/实付账本和提交读回语义，`dsh-assistant-fc-sbc-plan` 提供只读规划入口；`apps/chrome-extension/src/fc-sbc-page-probe.js` 与 `dsh-assistant-fc-sbc-probe` 提供基于当前文档的只读页面探针，能返回任务类型、可见挑战、市场权限文字线索和可见库存覆盖状态；`apps/chrome-extension/src/fc-sbc-inventory-snapshot.js` 定义完整库存快照合同，可把已读取的 club/SBC Storage/visible 卡行规整为可给求解器使用的实例清单，并标出缺身份、重复实例和覆盖未证明等阻塞项；`apps/chrome-extension/src/fc-sbc-transaction-readback.js` 定义交易读回合同，可把已观测到的购买新增卡、成交价、余额变化、提交后关卡完成和卡池变化分类成 confirmed/completed/unknown/blocked 等状态；`apps/chrome-extension/src/fc-sbc-field-audit.js` 将探针、完整库存快照和交易读回审计成 page/task/market/inventory/readback 字段覆盖与缺口；`apps/chrome-extension/src/fc-sbc-quote-preflight.js` 对同平台报价、新鲜度、正价和市场搜索上界做纯计算预检；`apps/chrome-extension/src/fc-sbc-execution-dry-run.js` 可从候选方案或批准快照生成无副作用的购买/提交执行预演队列，计算预算预留、每卡搜索上限和超预算/超搜索阻塞项；`apps/chrome-extension/src/fc-sbc-risk-preflight.js` 纯计算购买数、计划市场搜索数、提交数、市场可见性和未知交易读回数量，给出阻塞或谨慎状态，并明确不能证明不会封禁；`apps/chrome-extension/src/fc-sbc-approval-preview.js` 纯计算批准预览，把选中方案、预算、采购范围、提交范围、默认 10 分钟启动/60 分钟运行窗口、执行预演和风险状态汇成不可执行的审阅包；`apps/chrome-extension/src/fc-sbc-readiness.js` 与 `dsh-assistant-fc-sbc-readiness` 将页面、库存快照、交易读回、市场、字段覆盖、报价预检、执行预演、风险预检、批准预览和求解输入梳理成批准阻塞项、后续缺口与下一步动作，并把执行预演或风险预检的 blocked 状态纳入最终门禁；`apps/chrome-extension/src/fc-sbc-comb-report.js` 可生成带字段缺口、报价预检和批准预览摘要的脱敏第一道梳理交接摘要；`apps/chrome-extension/src/fc-sbc-redacted-sample.js` 可生成机器可读的脱敏样本包，并在有候选方案时附带执行预演、风险预检和批准预览、在有完整库存快照或交易读回时只附带聚合摘要；侧栏新增 `SBC` 只读梳理入口，可对已固定页面运行探针，显示阻塞项、字段覆盖、无副作用执行预演、风险暴露预检和批准预览，并由用户显式发送脱敏摘要或样本包到当前对话。真实 EA 完整俱乐部库存读取、真实市场权限验证、购买、填阵、提交和 EA 账号验收仍未实现。本文描述用户已确认的目标和当前源码可复用的边界；EA 页面字段、报价质量与具体执行手段仍需现场验证。

当前还新增了纯计算的 `apps/chrome-extension/src/fc-sbc-execution-gate.js` 合同，用于后续真实执行器在每个写动作前比较批准预览摘要、当前页面/会话身份、批准窗口、同标签写租约、购买价格上限和提交/填阵范围。它只返回 ready 或 blocked，不采购、不填阵、不提交，也不建立真实写租约；真实写租约派发和 EA 页面执行仍属于后续切片。

`apps/chrome-extension/src/fc-sbc-write-lease.js` 已补上配套的纯写租约记录，可签发、校验和释放绑定批准摘要与页面身份的限时租约；已释放租约会阻塞执行 gate。该记录仍只是未来真实租约派发的输入/审计合同，不会锁定浏览器标签页或拦截其它 Session 写动作。

## Epic outcome

用户在已登录的 FC 27 Web App 打开一组类似“重大比赛”的拼图 SBC，在 DSH 浏览器扩展中看到整组可执行方案：各关阵容、已有卡与待买卡、锁卡、卡牌机会成本、报价来源和时间、单卡最高价、金币总上限及最终提交范围。用户确认方案一次后，扩展依次购买缺卡、统一核对库存、填入各关并核验页面；确认范围内的提交继续执行。已完成关卡、实际花费、消耗卡牌、奖励和未决动作可回看。没有可证明的完成结果时，状态保持未决。

该能力服务个人自用。一次浏览器站点授权可持续使用；每个具体 SBC 方案仍由用户确认。方案确认是对列明采购与提交的授权，不要求逐卡或逐动作重复审批。模型可以提出方案，不能自行提高价格上限、扩大卡牌集合、改变任务或追认未决购买。

## 范围与任务分类

- 首个真实纵切是 FC 27 传统 11 人拼图 SBC 的一组多关任务；跨关规划，逐关购买、填阵和提交。
- 先识别任务类型。FC 27 另有按 Item Score 分次提交的简化 SBC；其部分提交也会永久耗卡，必须使用独立的模型与执行器，首个纵切不得套用拼图流程。
- 缺卡由扩展购买，用户不需逐张手动操作；首个版本只购买已批准方案所需的卡，不执行市场套利、倒卖、持续扫价或无上限循环任务。
- EA 对游戏内自动化的规则覆盖范围较广，自动购买仍有账号风险。减少市场操作量是工程上的风险控制，不能据此声称避免封禁；参见 [EA FC 规则](https://help.ea.com/en/articles/ea-sports-fc/fc-rules/) 与 [SBC 提交规则](https://help.ea.com/en/articles/ea-sports-fc/sbcs/)。

## 用户流程

1. 用户将扩展绑定到当前 FC 页面，选择整组 SBC。页面适配器读取挑战身份、各关要求、奖励、截止时间和已完成状态，并标记不可读字段；同时只读检查该账号在 Web App 上能否搜索与即时购买。没有市场权限仍可看方案，但不能批准带采购的执行。
2. 读取俱乐部与 SBC Storage 的卡牌实例，标记库存覆盖是否完整；当前源码已先落地纯计算的 `SbcInventorySnapshot` 合同，用于接收未来页面适配器读到的完整库存、去重实例、统计 Storage/锁卡/可交易卡并生成求解器输入，但它本身不读取 EA 页面。仅在覆盖足以避免重复购买后生成可执行方案。批准前重读库存，采购结束统一对账，每关提交后移除已消耗的实例并对账下一关所需卡；外部设备或人工操作使缓存失配时重新读取，不把旧缓存当权威。
3. 为候选待买卡获取与 FC 年份、平台、卡版本匹配的站外报价，保存来源、查询时间和可信状态。当前源码已提供纯计算报价预检：缺价、过期价、无效价、平台错配或超过市场搜索上界时阻止批准；它不联网、不采购，只消费已传入的报价样本。`0`、缺失或过期报价是未知值；购买时以 EA 当前挂牌价和批准上限为准。
4. 本地求解整组任务，共享库存约束，保护用户锁定卡，避免前一关耗掉后一关不可替代的卡。展示少买卡与省金币的候选方案及差异；用户选定具体方案。
5. 确认页一次列明任务、每关阵容与将消耗的具体卡、待买卡版本与数量、单卡最高价、总金币上限、允许的替代项、是否包含自动提交以及有效期。批准前可生成执行 dry-run 和批准预览，预览采购顺序、预算预留、每卡搜索上限、提交范围、默认 10 分钟启动窗口和 60 分钟运行窗口；这些预览不写浏览器、不购买、不填阵、不提交。用户点击执行后生成不可变批准快照；默认须在批准后 10 分钟内启动，并在批准后 60 分钟或最早任务到期时失效，运行中不延长。失效或方案变化只需重新确认方案，不逐卡审批。
6. 采购器按方案逐张搜索并购买缺卡。每笔发送前从总预算预留该卡最高价；确认成交后记实际支出并释放差额，结果不明则保留预留额度。每笔只核对该笔成交结果、成交价和余额，不重扫整个俱乐部；缺货、超价、购买结果不明或账号限制立即暂停。每卡最多两次市场搜索，不对同一挂单重复购买；采购次序优先试探替代项最少的卡。
7. 全部采购结束统一核对库存；仅在实际新增卡与方案一致时填入当前关。填卡后比对实际卡实例、锁卡状态和 EA 页面全部要求。
8. 提交前再次比较当前挑战、阵容和批准快照。若确认页包含该关提交且页面吻合，以稳定请求 ID 发送一次提交；该 ID 的重复调用只用于状态查询，不能把缓存的点击回执显示成完成。只有 EA 页面读回关卡完成和卡池变化后才继续下一关；明确拒绝且未提交时重新核验后才可创建新尝试。
9. 扩展显示实际花费、卡牌消耗、已完成关卡、奖励、被跳过动作与恢复原因。用户可停止后续动作；停止不撤销已成交购买或已提交卡牌。

当前源码已先落地纯计算的 `SbcTransactionReadback` 合同：它接收未来页面适配器读到的购买新增卡、实际价格、余额变化、提交前后完成状态与卡池数量变化，并把结果分类为 confirmed、completed、unknown 或 blocked。它不会搜索市场、不会购买、不会提交；同版本新增卡且实际价不超上限才算购买确认，提交必须同时看到关卡完成和卡池减少才算完成。

## 侧栏交互

扩展侧栏先显示整组进度、库存覆盖、市场权限、报价新鲜度和候选方案的买卡数量、估计花费及卡牌机会成本。当前已落地的 `SBC` 入口只做第一道只读梳理：对已固定页面运行探针，显示任务类型、市场线索、库存覆盖、可见关卡、阻塞项和后续缺口；它不采购、不填阵、不提交。字段覆盖审计会把稳定关卡 ID、要求/奖励行、市场权限证据、完整库存、SBC Storage、卡实例 ID、购买读回和提交读回分别标成 covered、partial 或 missing；当输入完整库存快照时，完整库存覆盖、Storage 和卡实例 ID 可以由快照证明；当输入交易读回时，购买确认和提交完成可以由已观测结果证明。报价预检会把缺价、旧价、错平台和市场搜索量过高变成批准前阻塞项，并把 quoteCoverage 带入摘要和样本包。执行 dry-run 会把候选方案转成只读采购/提交队列，显示预计购买数、预算预留、提交数、每卡搜索上限及副作用全为 false；它只证明“若批准，控制器将按此队列尝试”，不证明 EA 页面能成交、填阵或提交。风险预检会在同一只读边界内显示购买数、计划市场搜索数、搜索上限、提交数、未知交易读回数量和“不能证明不会封禁”的免责声明；超过购买、搜索或提交上限时阻塞批准，存在任何自动购买或提交暴露时至少标记为需谨慎。批准预览会在同一只读边界内汇总选中方案的预算、预留、购买数、提交数、启动/过期窗口和 required bindings；它只生成审阅包，不生成真实批准、不写浏览器、不购买、不填阵、不提交。侧栏还会生成一份可折叠的脱敏交接摘要，用户点击“发送给对话”后才把摘要提交给当前 Session；摘要只保留安全 URL、页面标题、可见计数、阻塞项、后续缺口、字段缺口、报价覆盖、批准预览摘要和可见要求/奖励行，不包含 URL 查询参数、私有实例 ID、卡牌文本样本或原始 DOM 片段。用户也可以点击“发送样本包”提交机器可读 JSON；样本包同样去掉 URL 查询、私有实例 ID、卡牌文本样本和原始 DOM，只保留字段覆盖、统计、要求/奖励行、市场线索、报价预检、执行预演、风险预检、批准预览、库存快照聚合摘要、交易读回状态摘要和隐私声明。选中方案后，同一视图展开各关用卡、保护卡、缺卡及价格上限；锁卡或排除关卡会重新求解，再由用户批准新方案。主命令清楚写明“执行并提交”或“购买并填阵”，确认页列出总预算和实际将提交的关卡。执行中按关显示已买/待买卡数、当前动作和最后可确认结果；未决动作保留原请求 ID，提供“核对结果”“确认未成交后继续”“停止并重新规划”入口，不显示虚假的完成百分比。停止后不发送新写动作，仍只读核对已发送的购买/提交，并将已完成、未开始和未决关卡分开显示。

## DSH 所有权与复用

| 角色 | 设计归属 |
| --- | --- |
| 浏览器入口 | 复用 `apps/chrome-extension` 的侧栏、会话、站点授权和固定页面身份。新增 FC 27 专属视图与页面适配器，不把 SBC 规则写进通用浏览器执行器。 |
| 浏览器动作 | 复用 `ctx.browser` 的会话、安装、授权 epoch、页面 `documentId`、请求 ID、回执和状态查询。通用动作的 `observed` 仅证明局部页面效果，SBC 完成必须由独立页面读回确认。 |
| SBC 定义 | 稳定的挑战、卡牌实例、报价、方案、批准范围、运行状态和结果合同；与具体 EA DOM、价格站、求解算法分离。 |
| 提供者 | FC 页面适配器、可替换报价源、本地约束求解器与按方案执行的采购/填阵控制器。先验证通用 Browser 动作能否覆盖 FC 页面；不够时才加领域动作。 |
| 消费者 | 扩展侧栏的方案与执行视图，以及可选的模型工具。SBC 任务 Session 的模型工具只提供读取与提出方案；采购和提交只接受带批准方案 ID 的领域执行命令，不把通用 Browser 写工具作为 SBC 执行入口。 |
| 持久事实 | Host/Session 记录批准方案 ID、版本、预算预留/实付流水、动作请求 ID、成交/提交回执和状态；俱乐部全量卡池为可重新读取的短期缓存，不存 EA 凭据或会话令牌。 |

现有 [浏览器定义](../../packages/browser/browser/src/types.ts) 已有页面身份、动作与请求状态；[浏览器工具](../../packages/browser/tool-browser/README.md) 的浏览器任务受模型续轮和动作预算约束，不能直接当作整组 SBC 的采购循环。方案执行应由确定性的领域控制器驱动，每个有副作用动作仍走现有浏览器授权、请求记录及未知结果恢复。

现有 [扩展](../../apps/chrome-extension/README.md) 提供个人部署的持续浏览器授权，但其通用审批策略不表达卡牌与金币预算：个人部署对同一动作类型不逐次征求同意，站点授权按安装与站点签发，只能证明某个已授权页面被操作过。因此卡牌集合与金币预算的唯一强制点是 SBC 域控制器，通用浏览器授权不构成 SBC 的执行边界。

SBC 控制器每次执行前校验批准方案、预算余量、卡版本、当前关卡和目标页面。运行期间还需占用该安装与标签页的写入租约：Browser 的操作意图和最终派发钩子拒绝其他 Session 对同一标签页的写动作，并只接受本控制器预先登记的请求 ID；读操作继续允许。租约须由持久运行状态恢复，终止及未决写核对后释放。租约只约束 DSH 的动作，不能阻止用户在 EA 页面或其他设备上操作；停机后普通浏览器授权仍存在，不把方案预算表述成全局浏览器限制。

## 最小领域合同

| 对象 | 必要字段与不变量 |
| --- | --- |
| `ChallengeSnapshot` | FC 年份、平台、任务组/关卡 ID、任务类型、要求、奖励、截止时间、完成状态、读取时间和覆盖状态；同时记录该账号的市场搜索/购买权限。运行绑定安装、标签页、俱乐部身份与授权 epoch，每次页面动作再绑定当前文档 ID。 |
| `CardInstance` | 具体卡实例 ID、卡定义/版本 ID、评分、位置、国家、联赛、俱乐部、稀有度、库存来源、可交易状态和锁定状态；同名或同球员的两张卡不可合并。 |
| `PriceQuote` | 卡版本 ID、平台、价格、来源、观测时间、有效期与未知/过期状态；站外报价只供规划，不能视为已成交价。 |
| `SbcPlan` | 每关具体卡实例和待购卡版本、价格上限、总预算、允许替代项、求解依据、报价引用、任务/库存版本、提交范围及有效期。 |
| `PlanApproval` | 用户直接确认的方案摘要、批准时间、启动期限与运行期限、绑定 Session/安装/标签页/俱乐部、单卡及总预算和可执行关卡；审批只对该版本生效。运行进程内用单调时间计时，重启后用持久 UTC 时间保守判定过期。 |
| `ActionLedger` | 每次购买、填卡、提交的稳定请求 ID、预期效果、发送状态、页面读回、实际价格及未知结果；购买前持久预留单卡上限，确认后记实付，未知保留预留，所有已付与预留之和不超过总预算；不会把“点击成功”升级为“交易或任务完成”。 |

库存可用性、整组要求和锁卡是硬约束。求解器在可行解之间比较需买卡数量、实际金币支出上界及已有可交易卡的机会成本；不可交易卡和 SBC Storage 重复卡使用独立的保留价值，不按零价值处理。展示低市场操作数和低金币成本的非支配候选，用户选中的方案及其上限才进入批准快照。

## 运行状态与恢复

`draft -> approved -> acquiring -> acquired -> filling -> ready -> submitting -> verifying -> completed` 是拼图 SBC 的正常路径。`blocked`、`unknown`、`cancelled` 保留最后已确认的动作与不可逆结果，恢复从读回现状开始。批准后不自动改任务、不扩大卡池、不提高价格；页面或授权变化使后续动作停止。允许的替代项只能在批准的版本、数量和价格上限内使用。

- 购买未发送且确定失败：可以选已批准替代项或报告缺货；不对市场做无限刷新。
- 购买已发送而结果不明：查询原请求 ID 和 EA 页面/金币/卡池状态，保持预算预留且不重发该挂单。证实未成交后，可以在剩余批准范围内对新挂单使用新请求 ID；仍无法判明则由侧栏引导用户核对或放弃后续任务。
- 填卡局部失败：保留现有阵容，读回实际槽位后决定补齐或重新规划；不得按旧槽位引用继续。
- 提交已发送而结果不明：查询关卡完成状态及库存变化，不能重发同一请求；明确未提交且原动作结束后，重新验证阵容才可开始新尝试。
- 任务、价格、锁卡或库存变化超出批准快照：生成新方案并等待用户确认；浏览器持续授权不替代方案授权。停止仅阻止新写动作，在途请求继续只读核对直到归入已成交、未成交或未决。

正常路径对速度的要求是一次有覆盖证明的库存同步、候选卡站外批量报价、一次整组求解、每张缺卡按需市场搜索和成交、购买完成后一次全量对账。验收记录每关耗时、EA 页面操作数、市场搜索数、实际与报价偏差；先以真实页面建立基线，再确定可持续的数值目标，不以随机等待作为性能或安全指标。

## 风险控制与证据

| 阶段 | 主要风险 | 控制与独立证据 |
| --- | --- | --- |
| 库存读取 | 漏读造成重复买卡或误用主力 | 覆盖状态、实例去重、锁卡确认；采购前不以未读视为不存在。 |
| 报价 | 卡版本/平台错配或价格过期 | 来源和时间可见；未知价不参加自动采购；市场挂牌再核对上限。 |
| 购买 | 账号限制、误买、超预算或未知成交 | 只采购方案缺卡，精确版本匹配、总/单卡预算、逐笔回执、结果不明停机。 |
| 填阵 | 选错同名卡或页面漂移 | 精确卡实例与页面身份绑定，每槽读回，全部 EA 条件全绿。 |
| 提交 | 已有卡不可恢复、重复提交 | 已批准关卡和阵容逐项比对，一次提交，读回关卡状态。 |
| 运行数据 | 登录信息泄露、远程代码漂移 | 不采集凭据/令牌，不把全量库存发送给第三方求解服务；锁定经审查的本地代码。 |

这些措施针对错误和不必要的操作；不将节奏模拟、随机延迟或页面事件类型宣传为防封保证。

[FodderGG](https://www.fodder.gg/features) 是 FC 27 用户体验参照，现行用户脚本动态加载远端客户端，求解依赖其服务；未确认可并入 DSH 的现行源码许可，不直接复制或依赖私有接口。[NoBrain SBC](https://github.com/harveyhu2012/nobrain-sbc) 的 MIT 代码可评估算法和取价适配，但 FC 27 规则及结果质量需要重新验证。[AutoPilot-SBC](https://github.com/icysymmetra/AutoPilot-SBC) 有 FC 27 扩展和求解代码，但为 GPL-3.0，不能未经许可直接并入 MIT 的 DSH。GitHub 球员数据只提供卡定义候选，不代替用户库存或实时价格。

## 当前真实页面样本

2026-09-25 在已登录的 FC 27 Web App“重大比赛”页面只读观察到四个挑战。挑战行使用 `.ut-sbc-challenge-table-row-view`，当前选中关的要求是 `.sbc-requirements-checklist li`，奖励名称是 `.ut-sbc-reward-table-cell-view--label`；切换挑战行后可分别读取四关规则，未见行级稳定挑战 ID。探针因此只把当前选中关的要求和奖励视为已读，其他关保留可见标题和临时位置 ID；位置 ID 不可用于购买、填阵或提交身份绑定。

该 SBC 页面仅显示“转会”导航，不能证明账号拥有市场搜索或购买权限；页面也没有完整俱乐部和 SBC Storage 库存。登录页有 `#Login.ut-login`，必须先进入账号后才能识别任务。此轮实页观察只切换挑战列表行并恢复原选中关，没有搜索市场、购买、填阵或提交；T0 的完整库存、市场权限和交易读回仍缺实页证据。

## 待验证事实

- 当前 FC 27 页面能否只凭已加载视图和有界翻页得到完整的俱乐部、SBC Storage 与唯一实例 ID；若不能，领域适配器可读取哪些已加载数据。
- 当前市场搜索、挂牌、购买确认和库存变化的页面证据是否足以区分成功、失败和未知；市场权限是批准采购前的必检事实，T0 需确认读取方式与无权限页面表现。
- 当前拼图任务要求的评分、化学及特殊卡语义，与本地求解器结果是否一致；简化 SBC 具体如何识别。
- 可用报价源的访问许可、FC 27 平台与卡版本覆盖、更新延迟及降级策略；第三方代码候选的许可和依赖边界。
- 当前扩展 WIP、构建产物和用户安装版本是否一致；本设计不将仓库源码存在视为运行时能力。

## Deferred / Open Questions

下列条目保留审查原文供追踪；已确认的采购前置检查、库存再同步、预算预留、批准期限、跨 Session 写入和未知结果恢复已进入上文，未经过逐项复核的意见不自动成为需求。

### From 2026-09-25 review

- **库存缓存短缺会让提交阶段复购已消耗卡** — 用户流程（P0，adversarial，confidence 75）

  增量更新只跟踪本扩展经手的动作，而俱乐部会因手机 App、网页端手动操作与奖励发放而变化。缓存一旦偏离 EA 实际库存，求解器就会把已消耗的卡当作可用卡填入阵容，提交时被 EA 拒绝；预算账目也会虚高。全文没有任何一步要求重新全量读回并重建卡池权威。

- **转会市场权限是前置准入门槛，不是待验证问题** — 待验证事实 / 最小领域合同（P0，adversarial，confidence 100）

  文档把「该账号是否已授予转会市场权限」列为待办问题，却把 SBC 提交「已有卡不可恢复」当作同级风险。权限缺失时采购会在中途成批失败，而用户此时已完成读出挑战、报价、整组求解与一次确认的全部投入，并且可能已买下前面几张卡——这些卡已进入俱乐部且很可能正是为后几关准备的关键卡。

- **采购循环没有节奏或重试上界** — 范围与任务分类（P1，security-lens，confidence 75）

  采购器本身就是「按方案逐张搜索并购买缺卡」的循环，而「减少市场操作量」是文档自述的工程风险控制。整组多关任务的缺卡可达数十张，每张都产生一次市场搜索与购买确认；缺货停机后没有任何规则限制恢复时重新发起搜索的次数与频率。账号封禁是不可逆损失，缺少节奏上界意味着暴露量随方案规模单调增长而无人设限。

- **批准有效期从未定义，一次点击变成长期委托** — 最小领域合同 / 运行状态与恢复（P1，security-lens，confidence 75）

  `SbcPlan` 与 `PlanApproval` 都声明含有效期，但全文未给出该期限的值或判定方式。Epic 承诺用户确认一次后扩展依次购买、填阵并提交一组多关任务，而挑战自带截止时间，实际执行窗口跨越数小时至数周。任何持有已批准方案 ID 的路径都能在此期间继续花钱，而用户对「购买」的心理授权通常只覆盖当次坐下来的时段。

- **「只发送一次提交」缺少实现机制，重试会拿到假成功** — 用户流程（P1，adversarial，confidence 75）

  现有请求记录语义与此冲突：请求 ID 一旦被记为非 unknown 的结果，再次派发同一身份会直接返回缓存回执而不重新执行。当 EA 因会话过期或页面漂移拒绝那次提交时，扩展已留下 observed 的投递记录，用户重试会拿到「已提交」的旧回执，而 EA 侧实际从未提交——卡永远填不进去，界面却显示该关已完成。

- **「结果不明不再点 Buy Now」落成永久停机** — 运行状态与恢复（P1，adversarial，confidence 75）

  EA 转会市场的挂单会被他人买走。一笔结果不明的购买若在查询期间原挂单消失，就永远不会出现「证明没有成交」的证据，该卡永久停留在未决状态，与 Epic「依次买齐缺卡」的目标冲突。缺口在于该规则把「禁止重复提交同一笔购买」写成了「禁止对同一张卡发起任何新的购买尝试」。

- **报价新鲜度只用墙钟时间戳判定** — 最小领域合同 / 风险控制与证据（P1，adversarial，confidence 75）

  报价保存的是观测时间与有效期，而时间跨度覆盖浏览器睡眠、系统休眠、时区与夏令时切换、NTP 校正。休眠数小时后醒来，单调时钟与墙钟的差距会让全部报价被判过期；而「未知价不参加自动采购」意味着求解器拿不到可用价格，自动采购被整体关闭，用户看到的归因会指向报价源故障而非本地时钟身份缺失。

- **SBC 写入边界只挡住本 Session，未挡住同页面的其他 Session** — DSH 所有权与复用（P1，adversarial，confidence 75）

  站点授权按安装与站点签发，因此同一 Host 下任何其他 Session 的通用浏览器写工具，只要拿到同一个已授权页面，就能对同一批 DOM 控件执行等价的搜索、Buy Now 与提交点击，完全绕开预算、卡版本与关卡校验。预算纯属 SBC 层的软约定而非执行层强制，越权路径没有任何检测环节。

- **运行级预算账本缺失，未知购买恢复后可能超额** — Epic outcome / 持久事实（P1，adversarial，confidence 75）

  持久事实只列了批准方案 ID、版本、预算、请求 ID 与回执，没有一条是在成交确认后才发出、可累加的支出记录。恢复路径要求读 EA 当前金币余额反推已花费金额，但只要期间有比赛奖励、每日任务或账号内其它消费，把「上限 − 已花」从余额反推就是错的，采购器会基于错误余量继续下单。

- **既有审批面未做复用分析** — DSH 所有权与复用（P1，scope-guardian，confidence 75）

  扩展已提供会话绑定、授权 epoch 约束、请求 ID 与请求数量上限的审批面，文档却只把它当作「侧栏、会话、站点授权和固定页面身份」并断言其审批策略不表达预算。把既有审批面当成假定的缺口而非 T0 待探明的现状，有重复造轮子的风险。

- **六个合同与十二个状态无逐切片归属** — 最小领域合同 / 运行状态与恢复（P1，scope-guardian，confidence 75）

  T0 与 T1 明确无副作用，只需挑战、卡实例与报价三个合同；方案、批准与动作台账属 T2 及以后。交付表没有把任何合同归到其首个消费切片，实现者无从判断 T0/T1 允许引入什么，风险是六个合同为可能延后的切片一次性建好。

- **状态机固化了被推迟任务类型的形状** — 运行状态与恢复（P1，scope-guardian，confidence 75）

  状态链假设单一的购买-填阵-提交流，而文档明确简化 SBC 必须使用独立的模型与执行器，即这套状态是按首个纵切不实现的任务类型建模的。同时 T2 与 T3 是可分别关闭的切片，首个纵切只会经过其中一个状态子集。

- **五个切片从未给出最小变更基线** — 交付切片与验收（P1，scope-guardian，confidence 75）

  文档定义了 T0–T4 并以自动采购、填阵、提交收尾，却从未说明交付 Epic outcome 的最小修改集。若 T1 的只读整组方案已交付 Epic 大部分可观察价值，则 T2–T4 需要各自承担其账号风险的理由；没有这个基线，无法判断自动采购栈是目标要求还是目标的邻接物。

- **确认页无法排除个别关卡或个别卡** — 用户流程 / 侧栏交互（P1，design-lens，confidence 75）

  批准范围横跨多关的采购与不可逆提交，但侧栏只有「执行并提交」与「购买并填阵」两个整体按钮。用户若只想执行前三关、或接受某张卡但不接受另一张，界面里没有可操作位置，只能整体接受或整体放弃——而整体放弃意味着重新走一遍规划与报价。

- **停止后未说明在途的已发送购买与提交由谁处理** — 用户流程 / 运行状态与恢复（P1，design-lens，confidence 75）

  停止被定义为不撤销已成交购买或已提交卡牌，但购买或提交通常正处于「已发送而结果不明」状态，金币与卡牌是否已消耗不可知。侧栏只承诺未决动作保留请求 ID 和可查询状态，没有说明停止后由扩展继续读回还是需要用户自行核对，而这类动作在 EA 侧不可撤销。

- **未决状态恢复后在界面上没有入口** — 运行状态与恢复 / 侧栏交互（P1，design-lens，confidence 75）

  文档要求未决动作只能由用户处理，但侧栏只描述可查询状态，没有重试、确认未成交后继续、或放弃并重规划的控件。用户看到一个停住的方案时无法判断下一步该点哪里，恢复路径在界面上断开。

- **停止后「已提交关卡」与「未提交关卡」在结果中不可区分** — 用户流程（P2，design-lens，confidence 50）

  停止可能发生在某一关提交之后、下一关采购中途，此时用户最需要知道哪些关卡已真的提交、哪些还没动。结果展示只列出已完成关卡与被跳过动作，处在中间态的关卡既非完成也非跳过，用户核对金币与卡牌消耗时无法对齐。

- **站外报价源的传输内容与降级策略未定义** — 风险控制与证据 / 外部复用决策（P2，security-lens，confidence 50）

  设计把边界划在库存上并承诺不发送全量库存，但报价请求本身要携带与 FC 年份、平台、卡版本匹配的候选卡标识——一份按平台与版本筛选过的候选清单已泄露持仓方向与目标 SBC，逐张采购还会在时间上暴露购买意图。风险表声明了要防的事，正文未给出对应的出站字段白名单与降级行为。

- **未知结果恢复依赖的查询窗口未覆盖完整对账周期** — 运行状态与恢复 / 最小领域合同（P2，security-lens，confidence 50）

  规则成立的前提是请求记录在用户回来处理之前仍可查，而现有请求记录的保留受窗口约束。若用户在购买后关闭扩展或 DSH 停机超过保留期，原始成交证据消失，「证明没有成交」这一步再也无法完成，该笔金币支出与卡牌归属都无法归因。设计把不可逆动作的安全性押在一个从未声明需要延长的窗口上。

- **缺少成交之外可用于事后归因的独立审计线索** — 交付切片与验收（P2，security-lens，confidence 50）

  验收证据全部落在 EA 侧的成交、库存、余额与奖励读回，而 EA 不回传任何与 DSH 批准方案对应的标识。事后重建「哪一次批准、哪个版本、花了多少金币、消耗了哪些卡」只能依赖 DSH 自己保存的记录，而设计未要求这些记录在 Session 之外持久留存或导出。

- **替代项在批准后才被具体选定** — 最小领域合同 / 运行状态与恢复（P2，security-lens，confidence 50）

  确认页只列出允许的替代项集合，而实际把哪张卡塞进哪个槽位由控制器在执行途中决定。用户批准的是集合、被执行的是集合中的某个具体元素，因此用户从未看到、也无法在看到之前否决那个真正被消耗的卡实例；提交会永久耗卡，落在集合内但违背本意的替换在提交后无法撤销。

- **不可交易卡的机会成本估值了一项目拒绝观测的量** — 最小领域合同（P2，scope-guardian，confidence 50）

  求解器被要求按已有可交易卡的机会成本排序，并给不可交易卡与重复 Storage 卡一个独立保留价值，但文档同时排除持续扫价、并把缺失或过期报价视为未知值。这迫使估值模型运行在计划有意不保持最新的数据上，而它服务的只是候选排序；一个按买卡数量与支出上界的非支配排序即可满足 T1 的比较需求。

- **T2 是唯一定稿证据要花真实货币的切片** — 交付切片与验收（P2，scope-guardian，confidence 50）

  T2 以真实低预算采购的请求与 EA 成交、库存、余额读回收尾，使其成为唯一无法在不产生不可逆花费的情况下验证的切片，而该账号风险正是文档自己标注过的。文档未说明单笔最小采购是否为预期的证据下限，也未说明采购路径是否需先走演练路径。

- **侧栏在方案选择前只显示两个候选方案** — 侧栏交互 / 用户流程（P2，design-lens，confidence 50）

  侧栏只展示两种方案的买卡数量与估计花费，而流程第 4 步说的是展示非支配候选。若求解结果中存在第三个非支配方案，用户看不到它，也无从判断这两项是否为全部可选空间；批准一次就是不可变快照，选错没有中途换方案的余地。

- **两个主命令的差异未说明** — 侧栏交互（P2，design-lens，confidence 50）

  「执行并提交」与「购买并填阵」并列出现且都会成交购买，但文档未交代二者在批准范围上的区别——是否包含自动提交、提交哪些关卡。用户点按钮时必须自己推断哪一个含不可逆提交。

- **机会成本在方案列表层不展示** — Epic outcome / 侧栏交互（P2，design-lens，confidence 50）

  Epic 承诺用户看到每张卡的卡牌机会成本，但侧栏在方案选择阶段只显示买卡数量与估计花费，展开细节是在选中方案之后。而不可交易卡与 Storage 重复卡有独立保留价值、不按零价值处理，这恰是方案之间的主要差异来源——用户在做出选择的那一刻拿不到这个数字。

- **库存覆盖不足时只报告状态，未定义可见的阻断原因** — 用户流程 / 风险控制与证据（P2，design-lens，confidence 50）

  规划被设计为仅在覆盖足以避免重复购买后生成可执行方案，即覆盖不足时用户看不到任何方案。这是扩展主动不提供结果，而不仅仅是没有方案可选；侧栏虽显示库存覆盖，却没说覆盖不足时用户看到什么、需要做什么才能解除，用户会面对一个空白方案区而不知道是被阻断。

- **「不显示虚假的完成百分比」缺少状态可读性替代方案** — 侧栏交互（P3，design-lens，confidence 50）

  文档正确地拒绝虚假进度，但只说了不显示什么，没有说明执行中用户实际看到什么来表示还在进行。整组采购可能持续很久，用户在没有任何进度承诺时无法区分正在推进与已经卡死，而后者的处理方式完全不同。
