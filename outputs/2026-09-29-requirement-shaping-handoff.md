# GPT 网页续聊交接：共同发展构想的 Skill

交接日期：2026-09-29。语言：中文。用途：上传到 GPT 网页，继续当前设计讨论。

## 1. 接手位置与第一条消息

当前在设计一个暂名为「需求澄清与成形」的 Skill，候选标识为 `requirement-shaping`。用户要求用这套方法澄清与成形它自己，已经实际讨论了一轮，并回答了一个影响默认行为的选择题。

用户刚刚明确选择：

> 共同改进构想：澄清目的，也主动提出遗漏、替代方案，用具体结果供我比较（推荐）。

这个选择已经确定，无需重问。名称、全部行为规则、输出格式和实现方式仍未全部确认。这个新 Skill 在本轮尚未写成或安装为正式 `SKILL.md`，也没有完成效果验证。

可以将下面这段作为网页新对话的开场消息：

> 请阅读交接文档，继续用「需求澄清与成形」这套方法来发展这个 Skill 自己。我已经选择“共同改进构想”：你应澄清目的，也主动提出遗漏、替代方案，用具体结果供我比较。请沿用已有上下文，区分我明确确认的要求与你提出的建议，继续拿出能让我具体判断的内容。不要仅复述交接、重复问已回答的问题，或立刻把所有建议定为硬规则。

本文是上一位助手整理的交接材料。引号中的用户原话及明确选择属于用户意见；标为建议、草案和待讨论的内容不具有同样的确认程度。网页端的新指示优先于这份交接。

## 2. 为什么会讨论到这个 Skill

用户在开发 DeepSeek Harness（DSH），期间发现一些项目 Skill 可能带来过重流程、过时规则、无关工作、反复确认和代理开销。问题由此转向：如何判断常用且重要的 `dsh-*` Skill 是否真的有正向价值，以及如何据此修改它们。

讨论中已经出现过这些纠偏：

- 不能把文档符合模板、遵守步骤、检查通过，当成实际效果好。
- 评价要有直观产物、可观察指标，也可以有需要解释的质量判断；不能全部是难以量化的自评分。
- 用户不愿把日常 Skill 改进建立在普通人难以执行的大规模对照实验上，希望利用别人已经做过的评测、优秀实现和真实使用证据。
- 用户不是禁止模型参与评估；此前助手强调“全程不调用模型”被用户明确反对。重点是衡量质量，不是围绕 token 作设计。
- 不能过度信任 `skill-creator`；它是可参考的工具，不能替代用途判断、外部证据和实际反馈。

随后用户提出：用户或 Agent 通常无法一开始就给出最合适的用途描述，多轮加工可能更有帮助。讨论进一步扩展到：除了用途，还有哪些内容值得澄清、查证、提炼、比较或演示。用户认为这套方法本身值得成为一个 Skill，并要求它“用自己来澄清与成形自己”。

当前主线是发展这个通用方法型 Skill。它与“评价和修改 Skill”的工作相关，但两者不要混为同一个已经完成的功能。

## 3. 用户明确表达过的要求

### 3.1 与当前设计直接相关

用户原话：

> 用户或者agent通常不会直接自然语言就能给出最好最合适的用途形容，如果用几轮提示词来优化它，会不会显著提升效果？

> 除了用途这个字段外，还有哪些需要这种澄清或其他手段加工以提高质量？

> 如果是你说的「需求澄清与成形」Skill，那你用它来澄清与成形它自己试试。

最新选择已经确认：默认侧重共同改进构想，包括主动提出遗漏与替代方案，用具体结果供用户比较。这是默认侧重，不意味着排除准确理解现有意图的能力。

### 3.2 相关长期取舍，保留原始语境

在之前的 Planning 需求讨论中，用户说过：

> 先想清楚收益和潜在副作用，允许为空，这些很多都是我没确认的，别稀里糊涂就把我的需求限制死了，怎么改？

> 我觉得这种细分工作应该在计划系统里完成，而不是在提交想法、需求时由提交者做。

对当前 Skill 的合理应用是：允许输入不完整；不要要求用户先做好分析；不要把助手补充的边界、非目标或假设直接写成用户已确认的约束。这种应用是根据原话作出的设计推导，不是用户已经批准某套固定数据结构。

用户在 Skill 评价讨论中明确表示，触发可以由自己发起，不需要自动评估或定时流程。这个要求已经落实在现有 `dsh-skill-quality` 上；新 `requirement-shaping` 的技术触发配置尚未决定，不能直接将前者的配置当成后者已确认的要求。

用户明确要求：除非用户明确要求，否则不要使用子代理。当前交接没有新增代理授权。复杂、可并行或某个参考 Skill 建议使用代理，都不构成授权。

## 4. 自用这一轮实际发生了什么

### 起始提案

助手最初将它定义为：从不完整的想法、现有材料和具体反馈出发，帮助用户发现、表达和检验真正需要的结果，逐步形成足以行动、仍可修正的需求。

助手提出它可用于 Skill、产品功能、Agent 工作流和研究报告，但这组适用范围是候选设计，不是用户逐项确认过的范围清单。

### 第一处修正

助手认为原定义过于强调“形成需求说明”，提出将目标调整为：帮助需求更值得做、更容易判断和推进；需求说明只是可能产物之一。

这是助手建议。用户随后确认了“共同改进构想”的默认侧重，但没有逐句确认“更值得做”等表述或赋予 Agent 最终决定用户目标的权力。

### 已回答的选择

问题比较了两种默认侧重：

1. 共同改进构想：澄清目的，也主动提出遗漏、替代方案，用具体结果供用户比较。
2. 优先对齐意图：准确理解用户提出的方向，再明确结果、标准和必要条件。

用户选择了第一种。两者是侧重差异，不是只能拥有其中一种能力。

### 选择后的修正

助手指出另一处缺口：先前只是列出加工方法，没有充分说明怎样产生有价值的新方向。因此提出补入以下做法：

- 检查目标与实现手段是否混在一起。
- 提出会改变实际行为或结果的备选，而不只替换措辞。
- 从资料、案例和使用场景中发现用户尚未提出的机会与问题。

这些是当前候选规则，还没有通过更多真实任务证明其有效性。

## 5. 当前可继续修改的核心草案

### 用途草案

> 和用户共同发展构想：理解想达成的结果，主动发现遗漏与新的可能，用资料、候选方案和具体样例帮助比较，逐步形成值得推进的方向。

### 行为草案

> 先利用已有对话和材料恢复用户的目的、明确要求和开放问题。
>
> 找出当前最影响结果的疑问或改进机会，选择提问、查证、提出备选、制作小样或推演使用场景。
>
> 提出的备选应体现实际行为或结果的差异，并说明理由与取舍。
>
> 根据反馈更新当前构想，明确哪些被采纳、哪些仍是建议、哪些需要验证。
>
> 当信息已足够时，形成可执行的方向；仍有关键未知时，给出能消除它的具体研究或试验。无需补齐所有字段。

这些是拟写入 Skill 的指令草案，并非已经安装、测试或全部获得用户确认的最终文本。

### 两种候选入口

| 入口 | 如何工作 | 适合的情况 |
| --- | --- | --- |
| 从理解开始 | 恢复共识，定位重要疑问，再提问或查证 | 背景复杂，事实和约束显著影响方向 |
| 从样例开始 | 先给简短候选结果，根据用户比较与修正提炼要求 | 用户难以描述偏好，但看见结果能够判断 |

助手建议保留两种入口，按当前困难选择，不必固定问答轮数。这个建议尚待进一步检验。

本次已经有较多背景，再问“你想让它有什么用途”很可能重复。更有价值的下一步可能是展示它处理具体需求的输出，让用户判断；这是接手建议，不是新任务指令。

## 6. 方法库：加工什么、怎样加工

下面是先前讨论形成的候选方法库。它不是每次必填的表，也不是必须逐项执行的流程。

| 内容 | 加工方法 | 希望产生的结果 |
| --- | --- | --- |
| 用途与价值 | 恢复语境、比较候选解释、观察具体结果 | 明白要帮助谁作出什么改变 |
| 成功标准 | 比较勉强、合格、优秀的结果；分析真实失败 | 能区分好坏的依据，减少空泛形容词 |
| 最终产物 | 制作小样，吸收反馈 | 明确真正需要的结论、文件、改动或其他结果 |
| 适用范围与触发 | 比较典型场景和相似但不适用的场景 | 判断何时介入、跳过或交给其他能力 |
| 输入与上下文 | 从真实任务倒推，检查能否自行获取 | 必需信息、可选信息及来源 |
| 专业知识与事实 | 查当前代码、权威资料、成功经验、公开评测 | 有来源和适用前提的具体知识 |
| 方法与决策规则 | 从案例提炼，使用不同场景检验分支 | 在什么条件下采取什么行动 |
| 约束与自主权 | 区分用户要求、环境事实、助手建议 | 必须遵守、可自行判断、尚未决定的内容 |
| 异常与停止 | 分析已发生的失败，推演关键异常 | 恢复办法，以及完成、暂缓或需要用户参与的条件 |
| 示例与表达 | 比较代表性正反例，检查照抄风险 | 清楚的判断方法和可理解的指令 |
| 与其他 Skill 的关系 | 检查重复规则、依赖和冲突 | 职责分工，减少重复工作和无关调用 |

选用加工方法的示例：意图不清时展示候选结果；接口过时时查当前事实；规则正确但适用条件模糊时补观察条件；只是怀疑一条规则无价值时先找证据，不直接删除。

## 7. 成功标准目前讨论到哪里

助手提出了以下可观察标准，尚未形成最终评估协议：

- 用户能通过具体样例作出选择，而不需要先熟悉需求工程的术语和表达方法。
- 新形成的要求能够说明依据，未确认建议保持可辨认。
- 用户纠正后，受影响的内容跟着修改，而不只是口头答应。
- 能指出一轮工作解决了什么疑问、发现了什么机会，以及如何影响下一步。
- 产物更长、措辞更漂亮、表格更完整，不能单独当成质量改善。

当前真实观察只有：用户通过一个行为差异明确的选择题确认了默认侧重，助手随后调整了草案。它证明这一处偏好得到表达和吸收；不能证明该 Skill 的总体增益、泛化能力或稳定性。

仍需解决：如何评判“新方向确实更好”，怎样避免模型自说自话，以及怎样用普通用户可接受的方式看到实际价值。不要未经讨论就给出一个固定分数阈值，或默认要求大规模模型实验。

## 8. 与现有 Skill 质量工作的关系

建议的分工是：

| 对象 | 当前作用 |
| --- | --- |
| 候选 `requirement-shaping` | 共同发展想法，明确值得追求的结果、比较依据和下一步 |
| 已有 `dsh-skill-quality` | 评价现有 Skill 的实际作用、当前适用性、副作用，形成保留或修改建议 |
| `skill-creator` | 编写与封装 Skill 的参考工具；不能独自证明内容有效 |

新 Skill 可以帮助形成“评价与修改 Skill”的用途与行为要求。两者是否共享参考材料、如何衔接，尚未确定；不要自动串联执行所有相关 Skill。

### 现有 `dsh-skill-quality` 的真实状态

本次交接前回读了本地文件，当前存在以下内容：

- 由用户手动触发；`agents/openai.yaml` 中有 `allow_implicit_invocation: false`，frontmatter 中有 `disable-model-invocation: true`。
- 主流程依次强调独立定义成功、分维度衡量、对照判断增益、量化结果、校准裁判。
- 评价维度包括任务结果、判断质量、范围与自主性、可靠性、当前适用性和副作用。
- 允许使用模型参与试验和评判，反对仅以 token 或步骤服从衡量质量。
- 参考材料包括案例、测量矩阵和第一批外部证据审查。

一个尚未处理的设计疑点：主文仍以实验和对照评估为重，而用户后来强调要利用外部已有结果、降低日常实施门槛。是否改成“证据审查与实际修改为常用路径，行为实验按需使用”，仍是后续可讨论的建议，不能说已经实现。

### 已进行过的本地修改

前期根据外部研究和本会话问题，调整了四个 Skill：

- `dsh-feature-delivery`：减少默认流程串联；相关步骤按实际未决问题选择；代理委派要求明确授权。
- `dsh-change-verification`：移除默认通用验证 Skill 依赖；较少用的自托管验证细节转入参考文件。
- `dsh-code-review`：按实际 PR 和受影响契约选择检查，修复一个旧链接。
- `dsh-reuse`：机械修改可跳过；社区搜索围绕本地缺口；非目标不由 Agent 擅自增加。

这些是修改事实与设计理由，不是已证实的本地效果提升。本次 Git 状态仍显示这四个文件及相关质量文档为未提交改动。网页端无需为了继续构思先处理提交、合并或部署。

## 10. 下一轮值得推进什么

下面是接手建议，不是新增的用户硬性需求，也不要求逐项完成。

1. 展示一次具体使用的小样，例如把“做一个评价和修改 Skill 的 Skill”作为输入，演示如何恢复已有要求、提出实质备选、取得证据和更新构想。用户已在当前任务中允许拿新 Skill 自身来试用，也可以继续围绕它自身制作小样。
2. 检查默认“共同改进构想”有没有足够的操作方法，能发现用户没想到的机会，同时保持建议与采纳之间的区别。
3. 用可见结果检验成功标准。例如要求中的一处歧义被具体方案区分、一个不成立的假设被事实修正，或用户反馈确实改变了下游输出。
4. 根据这些反馈整理简明的 `SKILL.md` 候选正文。不要先确定一张大而全的字段表，再要求用户把它填完。

仍开放的问题包括：最终名称、是否通用或带 DSH 定制、触发方式、默认产物形态、外部研究与样例制作何时介入、应保留哪些示例，以及如何观察效果。它们不需要一次性全部问用户；能查证的先查证，能从现有材料恢复的直接恢复，有实际行为分歧时再展示选择。
